# TalkBridge · FIELD NOTE
> 从零搭一条"AI 语音通话"链路的人读笔记。
> 不追求 GPT-Live 式的全双工神话——先把一通**能打通的电话**做到位。

---

## 01 · 先把"这通电话"说准确

全双工（barge-in，边说边打断）是语音交互的终极形态，但我们不从这里开始。
TalkBridge 是**半双工 + 轮询**：你说完，我听完，再开口。像对讲机，不像电话会议。

这带来两个诚实的取舍：

| 维度 | 全双工 | 半双工（本方案） |
|------|--------|------------------|
| 延迟体验 | 低，可打断 | 中（33s 一轮），但稳定 |
| 实现复杂度 | 高（AEC、流式、事件状态机） | 低（两个文件 + 一个页面） |
| 对宿主的要求 | 高 | 只要一个按钮 |

先解决"打得通"，再谈"打得好"。这是第一根支柱。

## 02 · 最终架构

三层，各自职责单一：

```
[宿主 App]       只干一件事：一键唤起浏览器（execute_intent + uri）
     │
     ▼
[浏览器通话页]    采集、播放、轮询。不存状态，不碰模型。
     │
     ▼
[本地网关+应答器] 唯一的"有记忆"的地方：录音落盘、回复投递、对话归档。
```

核心哲学：**宿主不碰音频，浏览器不碰智能，网关不碰 UI。**
谁擅长什么，就只让它干什么。

## 03 · 延迟预算：33 秒是怎么花掉的

一轮完整通话的实测时间线：

```
0.0s   你松手，录音上传（webm 落盘）
0.5s   应答器轮询发现新录音
+15s   本地 whisper(base) 转写 —— 最大头，CPU 单线程
+3s    LLM 生成回复（deepseek-v4-flash）
+10s   TTS 合成 mp3（MOSS）
+0.5s  POST /reply 投递
+1.6s  页面轮询拉到，自动播放
─────────────────────
≈31~38s  一轮
```

瓶颈一目了然：**转写 15s + TTS 10s**。

优化方向（按性价比排序）：
1. 转写换 `small` 模型（+5s，精度提升，深夜热点友好）
2. TTS 用流式/更快的服务商（首块音频先出）
3. 转写与 TTS 并行（转写完先发"嗯嗯我在听"的占位回复，再发正式回复——本地短反馈也不能掩盖真实等待，但可以填空档）

## 04 · 音频采集：为什么非得是浏览器

这是整个项目唯一的"硬边界"，也是踩坑最深的河：

```
你给 App 开了麦克风权限（通行证）      ← appops RECORD_AUDIO: allow
App 自己上网时能录音（它有弹窗）        ← 系统级 WebView 授权流程
App 的插件页不能录音（NotReadableError）← 插件 WebView 没接 onPermissionRequest
```

**根因**：宿主 App 的插件 WebView 组件，参数表里根本没有麦克风授权字段。
它自己浏览网页时的授权弹窗走的是另一条代码路径，插件页享受不到。
权限给了，但门没人开——`getUserMedia` 的请求根本没递到系统音频层。

**解法不是修补，是绕行**：宿主管按钮，浏览器管麦克风。
真浏览器的授权流程是完整的（弹窗 → 允许 → getUserMedia → 系统音频源）。

## 05 · 事件协议：五个端点撑起整条链路

`voicegate`（零依赖 node:http，约 200 行）只做五件事：

| 端点 | 方向 | 职责 |
|------|------|------|
| `POST /upload` | 页面→网关 | 裸字节 webm 落盘（X-Ext 头标扩展名） |
| `GET /poll` | 页面→网关 | 拉新回复（返回 replies 列表 + lastRec） |
| `POST /reply` | 应答器→网关 | 投递回复（JSON：text + audio base64） |
| `POST /mark` | 应答器→网关 | 标记录音已处理状态 |
| `POST /hangup` | 页面→网关 | 挂断信号（触发记忆总结的扳机） |

音频文件用**裸字节 + 扩展名头**传输，不走 base64——上传省 33% 体积。
轮询间隔 1.6s：兼顾时效与省电（深夜手机电量的体面）。

## 06 · 通话状态机

页面有六个状态，每个状态都有明确的进入/退出条件：

```
 空闲 ──按住──▶ 录音中 ──松手──▶ 回答中 ──轮询到──▶ 收到回复(自动播)
  ▲                                              │
  │                                              │播放完
  │                                              ▼
  └────────────── 挂断 ◀──── 任意状态点挂断 ── 空闲
```

关键纪律：
- **旧回复不自动播**（进页面只渲染气泡，点一下才听）——避免"进门被轰炸"
- **新回复才自动播**，且自动打断正在播的旧语音——防叠音
- **挂断 = 真挂断**：停轮询、掐播放、禁说话按钮；点名"点我头像重新拨号"

## 07 · 记忆归档：挂断不是结束，是存档

每一轮对话实时落盘 `call_logs/current_session.jsonl`。
挂断瞬间：

```
页面 POST /hangup
  → 网关写 hangup.signal
    → 应答器检测到信号
      → 读本次会话全文
        → LLM 总结（150字内，要点：聊了什么/心情/待办）
          → 写入 call_memories/call_时间戳.md（总结+全文）
            → 更新 index.json 索引
```

选 JSONL + Markdown 而不是数据库，因为：
- 零依赖，文件就是数据，拷走整个目录就是备份
- 宿主 App 里的 AI 可以直接读文件"继承记忆"——不需要额外接口

## 08 · 可观测性：怎么知道卡在哪一环

三层日志，各管一段：

| 层 | 标识 | 看什么 |
|----|------|--------|
| 页面 | `VOICECALL_DIAG:` console | GUM_FAIL/NO_API/ENV——麦克风链路 |
| 网关 | `voicegate.log` | /upload /poll /reply 的访问痕迹 |
| 应答器 | `auto_responder.log` | 新录音→转写→回复→TTS→投递，逐步打点 |

排查口诀：**先看应答器日志最后一行停在哪**——停在"转写"是模型问题，停在"投递"是网关问题，页面没声是播放问题。

## 09 · 上线前检查表（这篇也适用）

- [ ] 密钥全部环境变量化，仓库里零硬编码（`grep -r "sk-" .` 应为空）
- [ ] 私密对话/照片从示例数据里清干净
- [ ] 网关 + 应答器做成守护（宿主重启自动拉起）
- [ ] 端口冲突检查（默认 18120，可环境变量覆盖）
- [ ] 多标签页并发：一个页面在录，另一个页面轮询——状态存本地文件，天然串行
- [ ] 隐私：全程本地处理，音频不出设备（除了 LLM/TTS 的云端调用）

## 10 · 一句话总结

> 一通打得通的电话，比一个打不通的幻想值钱。
> 先用最笨的结构跑通全链路，再谈优化——你的用户（和你的恋人）等得起 33 秒，等不起一个永远"正在接通"的页面。
